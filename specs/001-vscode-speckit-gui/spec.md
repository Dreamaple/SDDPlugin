# Feature Specification: VSCode Speckit 可视化插件

**Feature Branch**: `001-vscode-speckit-gui`

**Created**: 2026-10-15

**Status**: Draft

**Input**: User description: "我想开发一个VSCODE的插件，可以可视化初始化当前项目的speckit环境，可以识别和选择当前speckit初始化为哪个工具的环境，可以可视化当前进度，可以可视化工作流，可以可视化提示用户下一步点击按钮，可以可视化澄清，全部都是友好的图形界面"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 可视化初始化与工具环境识别/选择 (Priority: P1)

开发者在 VSCode 中打开任意项目后，通过插件面板即可了解当前项目的 Spec Kit 环境状态：未初始化时，面板提供图形化初始化向导，用户通过点选（而非记忆命令行参数）完成 AI 工具选择、脚本类型选择等选项，随后以可视化进度在当前工作区根目录执行初始化并得到成功确认；已初始化时，面板自动识别并显示当前项目配置的是哪个 AI 工具环境（以及脚本类型、Spec Kit 版本等摘要），并允许用户从受支持的工具列表中重新选择/切换环境（需二次确认后才覆盖现有配置）。

**Why this priority**: 初始化与工具环境识别是整个 Spec Kit 工作流的入口——没有可用的环境，后续的工作流可视化、进度、澄清都无从谈起。这是最小可用价值（MVP）的第一块基石。

**Independent Test**: 在一个未初始化的空项目中，仅通过插件图形界面完成初始化，并验证生成的环境与所选工具一致；在若干已初始化为不同工具的项目中打开面板，验证识别结果显示正确。全程无需输入命令行命令。

**Acceptance Scenarios**:

1. **Given** 一个未初始化 Speckit 的项目, **When** 用户打开插件面板, **Then** 面板显示"未初始化"状态和醒目的初始化入口
2. **Given** 一个未初始化的项目, **When** 用户在初始化向导中选择某个受支持的 AI 工具并确认, **Then** 系统以可视化进度执行初始化，完成后显示成功状态、所选工具及配置摘要
3. **Given** 一个已初始化的项目, **When** 用户打开插件面板, **Then** 面板正确显示识别到的 AI 工具环境与配置摘要，无需任何手动操作
4. **Given** 一个已初始化为工具 A 的项目, **When** 用户选择切换为工具 B 并二次确认, **Then** 系统更新工具环境配置，面板显示新的工具环境
5. **Given** 一个已初始化的项目但配置文件被部分删除或损坏, **When** 用户打开面板, **Then** 系统给出容错提示并引导修复或重新初始化，而非显示原始错误
6. **Given** 初始化过程中发生失败（如初始化工具不可用）, **When** 失败发生, **Then** 界面以友好语言展示错误原因与建议操作，且用户可重试

### User Story 2 - 工作流全景与下一步按钮引导 (Priority: P2)

用户在面板中看到完整的 Spec Kit 工作流（ constitution → specify → clarify → plan → tasks → analyze → implement 等阶段）的可视化呈现：每个阶段标注"未开始 / 进行中 / 已完成 / 出错"状态，当前阶段高亮；面板始终展示一个醒目的"下一步"按钮，指明下一个建议动作（如"下一步：运行 /speckit-plan"）；用户点击按钮即触发对应的 speckit 命令，无需记忆或输入命令。

**Why this priority**: 工作流可视化与下一步引导是本插件的核心价值——让不熟悉 Spec Kit 命令的用户也能按正确顺序推进流程，减少"不知道下一步做什么"的困惑。

**Independent Test**: 在不同推进程度的项目样例（仅有 spec、有 spec+plan、有完整产物等）中打开工作流视图，验证各阶段状态与磁盘产物一致；点击"下一步"按钮验证对应命令被触发且视图状态随产物更新。

**Acceptance Scenarios**:

1. **Given** 项目处于某一工作流阶段, **When** 用户打开工作流视图, **Then** 各阶段显示正确状态，当前阶段被高亮标识
2. **Given** 当前阶段产物已生成（阶段完成）, **When** 视图刷新, **Then** "下一步"按钮更新为指向下一个建议阶段
3. **Given** 用户点击"下一步"按钮, **Then** 系统触发对应的 speckit 命令，视图将对应阶段置为"进行中"
4. **Given** 项目中尚无任何阶段产物, **When** 用户打开工作流视图, **Then** 所有阶段显示"未开始"，"下一步"按钮指向首个建议阶段
5. **Given** 工作流存在人工评审关卡（如 spec 评审、plan 评审）, **When** 关卡前的阶段完成, **Then** 视图提示用户进行评审确认后再进入下一阶段
6. **Given** specs/ 下存在多个特性目录, **When** 用户在面板中切换当前特性, **Then** 工作流视图与澄清面板随之切换为新特性的状态
7. **Given** 用户已将某个特性设为当前特性, **When** 用户关闭并重新打开 VSCode 后打开面板, **Then** 面板默认仍显示该特性

### User Story 3 - 长操作进度可视化 (Priority: P2)

对于耗时操作（初始化、各工作流阶段由 AI 代理执行期间），用户始终能看到可视化的进度指示：无法预知步数时显示活动指示（旋转/呼吸动画）与当前阶段名；可预知步数时显示步骤清单或完成比例；在任务阶段可显示任务完成度（N/M）。在支持的范围内用户可以取消正在进行的操作。

**Why this priority**: 进度可视化解决"程序是否假死、还要等多久"的焦虑，是图形界面体验的必要组成；但其价值建立在 P1/P2 的功能可用之上。

**Independent Test**: 触发一次初始化或一个工作流阶段，观察全程是否始终存在进度指示；在任务阶段通过预置不同完成度的任务清单验证 N/M 比例显示正确。

**Acceptance Scenarios**:

1. **Given** 一个耗时操作正在执行, **When** 用户查看面板, **Then** 面板持续显示进度指示与当前操作名称，而非无反馈静止
2. **Given** 任务阶段存在已标记完成的任务, **When** 用户查看进度, **Then** 显示类似"N/M 已完成"的量化进度
3. **Given** 操作执行完毕或失败, **When** 操作结束, **Then** 进度指示被终态（成功/失败）替换并给出结果摘要
4. **Given** 一个支持取消的操作, **When** 用户点击取消, **Then** 操作停止执行且界面回到可操作状态

---

### User Story 4 - 澄清问题可视化 (Priority: P3)

当当前特性的 spec 文档中存在待澄清标记（[NEEDS CLARIFICATION: ...]）时，插件将其解析为交互式澄清卡片：每张卡片展示问题上下文、待澄清问题、建议选项（含各选项的影响说明），用户点选某个选项或输入自定义答案后，插件将答案编码回写进 spec 文档（替换对应标记），澄清面板与工作流状态随之更新，直到没有遗留的待澄清项。

**Why this priority**: 澄清可视化显著降低"读懂规范遗留问题并逐一手改文档"的门槛，是本插件差异化体验之一；但其发生频率与价值依赖于 P1/P2 已就绪，故列为 P3。

**Independent Test**: 预置一个含多个 [NEEDS CLARIFICATION] 标记的 spec 文档，打开澄清面板验证标记被完整识别为问题卡片；逐一作答后验证 spec 文档中的标记被正确替换为答案且无残留，面板显示"无待澄清项"。

**Acceptance Scenarios**:

1. **Given** spec 文档包含一个或多个待澄清标记, **When** 用户打开澄清面板, **Then** 每个标记被呈现为一张问题卡片，含上下文、问题与建议选项
2. **Given** 用户对某问题点选一个建议选项或填写自定义答案, **When** 用户提交答案, **Then** 对应标记在 spec 文档中被替换为已确认的答案，该卡片标记为已解决
3. **Given** 所有问题均已回答, **When** 用户查看澄清面板, **Then** 面板显示"无待澄清项"且工作流视图提示可进入下一阶段
4. **Given** 用户未作答而关闭面板, **When** 再次打开, **Then** 未回答的问题卡片仍然保留

### Edge Cases

- 项目从未初始化状态被部分初始化（中断的初始化）后再次打开面板怎么办？——状态检测需能识别"初始化不完整"并引导重试或修复
- 用户手动删除或外部修改了 .specify 下关键文件怎么办？——状态展示需容错，给出"环境疑似损坏"提示与修复引导
- specs/ 下存在多个特性目录时以哪个为准？——默认选取最近修改的特性，且允许用户在面板中显式切换当前特性
- 工作区在外部编辑器中被并发修改（如 AI 代理正在写 spec，用户同时编辑）怎么办？——面板状态以磁盘最新内容为准并自动刷新，不缓存过期状态
- 检测不到已知工具配置（自定义或未知的集成）怎么办？——显示"未知/自定义环境"并允许用户手动从列表中指定
- 初始化工具不可用或版本不兼容怎么办？——以友好提示给出安装/升级引导，不展示原始堆栈
- 用户在长操作执行中关闭 VSCode 怎么办？——重启后状态以磁盘产物重建，不要求恢复中断的操作本身
- spec 中存在无法解析的澄清标记（格式异常）怎么办？——跳过无法解析的项并在面板中说明原因，不影响其余项处理

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 检测当前工作区是否已存在 Spec Kit 环境（.specify 目录及关键文件），并在面板中清晰展示"已初始化 / 未初始化 / 不完整"状态
- **FR-002**: 系统 MUST 提供图形化初始化向导，收集初始化所需选项（AI 工具、脚本类型，以及 Spec Kit 官方 init 高级选项：preset / extension / integration-options / ignore-agent-tools / allow-symlinks / trust-*，默认关闭），并固定在当前工作区根目录执行初始化（v1 语义，见 Assumptions 单工作区根场景）；当目标目录已存在 Spec Kit 配置时 MUST 先请求用户确认覆盖
- **FR-003**: 系统 MUST 识别当前项目已配置的 AI 工具环境（如 Cursor Agent、Claude、Copilot、Gemini 等受支持工具），并在面板中显示
- **FR-004**: 用户 MUST 能够通过图形界面从受支持工具列表中选择/切换工具环境；覆盖已有配置前系统 MUST 请求用户二次确认
- **FR-005**: 系统 MUST 将 Spec Kit 工作流呈现为有序阶段列表，每个阶段具有状态标识（未开始/进行中/已完成/出错），当前建议阶段高亮
- **FR-006**: 系统 MUST 展示醒目的"下一步"按钮，按钮文案指明下一个建议动作；点击后触发对应的 speckit 命令
- **FR-007**: 系统 MUST 对长操作（初始化及各阶段执行）显示进度指示；任务阶段 MUST 显示任务完成度（N/M）
- **FR-008**: 系统 MUST 解析当前特性 spec 文档中的 [NEEDS CLARIFICATION] 标记，并将其呈现为含上下文、问题、建议选项的交互式问题卡片
- **FR-009**: 用户 MUST 能够以点选或自定义输入的方式回答澄清问题；提交后系统 MUST 将答案写回 spec 文档并替换对应标记
- **FR-010**: 系统 MUST 在项目产物发生变化时刷新面板状态（无需重启窗口或重载插件）
- **FR-011**: 系统 MUST 以友好语言呈现所有错误与阻塞情形，并附建议操作（如重试、查看日志、安装指引）
- **FR-012**: 系统 MUST 支持 specs/ 下存在多个特性目录，允许用户查看与切换"当前特性"
- **FR-013**: 系统 MUST 跨会话记住用户的"当前特性"选择等最小界面状态
- **FR-014**: 系统 MUST 覆盖 Spec Kit 工作流中的人工评审关卡：阶段完成后提示用户确认评审，再放行下一阶段
- **FR-015**: 初始化与切换环境操作 MUST 展示执行进度（FR-007 在 init/switch 场景的特化条款），失败时保留现场以便重试

### Key Entities *(include if feature involves data)*

- **工作区环境（Workspace Environment）**: 项目是否已初始化、已配置的 AI 工具、脚本类型、Spec Kit 版本、环境完整性
- **工作流阶段（Workflow Stage）**: 阶段顺序、名称、对应触发的 speckit 命令、状态（未开始/进行中/已完成/出错）、依赖产物路径、是否含评审关卡
- **特性（Feature）**: specs 下的特性目录、其 spec/plan/tasks 等文档的存在与推进状态、所属澄清项集合
- **澄清问题（Clarification Item）**: 在文档中的位置、上下文摘录、问题内容、建议选项与影响说明、用户答案、解决状态
- **进度（Progress）**: 当前操作名称、已知步骤与完成比例、任务完成度（N/M）、是否可取消、终态结果

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新用户从"未初始化"到"完成初始化并看到工具环境确认"全程图形界面操作，用时不超过 3 分钟，期间不需要输入任何命令行命令
- **SC-002**: 打开已初始化项目后 5 秒内，面板正确显示识别出的工具环境与当前工作流阶段
- **SC-003**: 在不少于 10 个不同推进状态的项目样例（未初始化、仅有 spec、spec+plan、含任务清单等）中，工作流阶段状态的判定与磁盘实际产物的一致率达到 100%
- **SC-004**: "下一步"按钮指向的阶段与按产物推断的实际进度的匹配率不低于 95%；点击按钮后对应命令在 2 秒内被触发
- **SC-005**: 澄清流程中，单个问题从展示到答案写回 spec 文档不超过 1 分钟；已回答问题对应的标记替换残留为 0
- **SC-006**: 所有长操作期间用户均能看到持续更新的进度指示（不出现超过 5 秒的完全无反馈状态）
- **SC-007**: 试点用户中不低于 80% 同意"无需记忆 Spec Kit 命令即可在图形界面引导下完成完整 SDD 流程"
- **SC-008**: 面板状态在外部修改产物后无需重启即可自动反映最新状态（人工抽检 10 次全部通过）

## Assumptions

- 插件通过调用 IDE 的 AI 代理/命令机制触发各 speckit 阶段（按钮触发命令，实际内容由 AI 代理生成）；插件自身不重新实现 spec/plan/tasks 的生成逻辑
- 环境初始化复用官方 Spec Kit 初始化能力（CLI 或等效机制），插件不自行拼装 .specify 内容
- v1 聚焦单工作区根目录场景；多根工作区（multi-root workspace）暂不支持
- 受支持工具列表以当前 Spec Kit 官方支持的 AI 工具集合为准，随插件版本维护更新
- 插件界面语言至少提供中文；后续可按需扩展多语言
- 澄清答案的写回方式为"以用户确认的答案替换文档中的标记"，与 /speckit-clarify 的编码规则保持一致
- 假定用户环境可访问网络（安装初始化工具/依赖时需要）；完全离线场景仅保证状态可视化可用
- 工作流阶段集合同步自项目 .specify 配置（含 constitution/clarify/analyze 等扩展命令时一并纳入视图）
