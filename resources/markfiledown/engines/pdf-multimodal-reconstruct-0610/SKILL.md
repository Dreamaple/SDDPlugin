# PDF 多模态重建 Skill

## 定位

专门处理**纯图片PDF**（无内嵌文本的扫描版、Figma设计稿导出PDF等）的多模态Markdown重建。

与标准 text-first pipeline 的区别：
- 标准 pipeline：OCR文字为主，截图为辅助佐证
- 本 skill：**OCR文字证据 + Agent逐页读图重建** 双轨并行，交叉验证

## 何时使用

适用场景：
- Figma/Sketch 导出的设计稿 PDF（全页面截图）
- 扫描件/拍照版 PDF（文字为图片的一部分）
- 交互原型文档（含 UI mockup + 编号标注 + 交互说明）

不适用场景：
- 有内嵌文本层的 PDF（用标准 text-first pipeline）
- 只需要快速提取文字，不需要布局还原

## 工作流

### Phase 1：管线提取（获取证据素材）

```powershell
# 用 doc-pre-allinone pipeline 跑一次，关闭 agent review
.\doc-pre-allinone-skill-0508\run.ps1 \
  -InputFile "<pdf路径>" \
  -OutputRoot "<输出目录>" \
  -EnableAgentReviewValidation:$false
```

这一步产出：
- `source.md` — OCR 文字基线
- `artifacts/pages/page-XXXX-full.png` — 每页全页截图
- `artifacts/regions/page-XXXX-region-main.png` — 主内容区切片
- `artifacts/regions/page-XXXX-region-diagram-focus.png` — 说明区/标注区切片
- `artifacts/pages/page-XXXX-tile-rXcY.png` — 网格切片（辅助用，通常大量空白）

### Phase 2：Agent 多模态重建（核心）

Agent 逐页读图，产出 Markdown。关键规则见下方「读图策略」。

### Phase 3：产出校验

- 每页采用混合格式：段落文字 = Markdown，UI 元素 = ASCII
- 文档末尾必须包含 OCR-视觉修正对照表
- 检查编号标注区域是否完整覆盖

## 核心原则：忠实还原原PDF空间布局

**不要按功能/主题重新组织内容。** 产出的 Markdown 必须让读者能"像看原PDF一样"看到页面的空间结构。

- **错**：把同一功能的内容（主界面按钮 + 弹窗 + 说明文字）拆到不同区块
- **对**：按原PDF的视觉分区呈现 —— 上部 = UI截图区，下部 = 编号标注区，每个编号的说明和mini图保持原位置关系

每页的 ASCII 还原必须反映原PDF的**实际排版**：
1. 页面标题居中顶部
2. 主截图区（深色UI + 弹窗/箭头）
3. 白底编号标注区（逐编号，含对应mini图/流程图）

## 读图策略

这是重建质量的核心。按页面类型选择读取的图像：

### 规则 1：优先读 region，不读全页

| 页面类型 | 读哪些图 | 原因 |
|---------|---------|------|
| 全白底文字页（如规范说明页） | `full.png` | region 切分对纯白底无意义，全页足够清晰 |
| 深色UI截图 + 白底说明区 | `region-main.png` + `region-diagram-focus.png` | 全页截图太密看不清按钮细节；region 精准切到内容区域 |
| 混合布局页 | 先读 `full.png` 了解全局，再读对应 `region` 看细节 | 两步走 |

### 规则 2：不要依赖全部 tile

- 5×5 网格切分对**上暗下白**的双区域页面会产生大量黑/白空白 tile
- tile 只在 region 不够用时作为辅助（比如需要看某个特定角落）
- 看到大量空白 tile 时，直接忽略，不要浪费 token

### 规则 3：小字号 UI 元素必须放大确认

- 按钮文字、开关状态、Toast 文案等小字号内容，全页截图上可能模糊
- 读 `region-diagram-focus.png` 或对应 tile 来确认
- 不确定时，标注 `[OCR不确定，需视觉确认]` 而不是猜测

### 规则 4：编号标注区域要完整覆盖

设计稿页面底部通常有编号标注区（如 ①③④⑤），每个编号对应一个交互说明。
- 编号说明区通常在 `region-diagram-focus.png` 中
- 必须逐编号确认，不漏掉任何一个
- 编号说明区的文字通常比主界面文字清晰，优先以其为准

## 输出格式

采用**混合策略**：段落文字用标准 Markdown 格式化，UI 截图和流程图用 ASCII 还原。

```markdown
## Page N — [页面标题]

> [页面顶部警告/标注文字，用引用块]

### UI 截图区

[ASCII 还原原PDF中的 UI mockup、弹窗、按钮卡片等视觉元素]

### 编号标注说明

#### ① [编号标题]

[段落文字：用标准 Markdown 格式化——标题、列表、表格、行内代码等]

[如果该编号包含流程图/弹窗/状态流转，用 ASCII 还原]
```

### 格式分工

| 内容类型 | 格式 | 示例 |
|---------|------|------|
| 页面标题 | Markdown 标题 `##` | `## Page 4 — 车辆` |
| 警告标注 | Markdown 引用 `>` | `> ▲ 功能清单有...` |
| 段落说明 | Markdown 段落/列表 | `Tab 标签项支持上下滑动...` |
| 颜色/代码 | 行内代码 `` ` `` | `` `FF0000` `` |
| 表格数据 | Markdown 表格 `|` | 变更记录表、颜色对照表 |
| Toast 文案 | Markdown 列表 + 行内代码 | `- `"请在车辆上电状态进行操作"` ` |
| UI 截图 | ASCII 框线图 | 深色界面、按钮、弹窗 |
| 流程图/状态流转 | ASCII 箭头 + 框 | `[OFF] ──→ 弹窗 ──→ [ON]` |
| 弹窗/对话框 | ASCII 矩形框 | `┌──┐ │内容│ └──┘` |

### ASCII 还原要点

1. **忠实原PDF布局，不要逻辑重组**
   - 错：把"车锁"相关的所有内容（主界面按钮、弹窗、说明）合并为一个功能区块
   - 对：原PDF上部分 = 深色UI截图+右侧弹窗（ASCII），下部分 = 白底编号标注区（Markdown 标题+段落）

2. **ASCII 只用于视觉元素**：UI 截图、按钮卡片、弹窗、流程图、状态流转
   - 不要对纯文字说明部分做 ASCII 化

3. **按钮卡片要独立呈现**：不要合并为抽象流程图
   - 错：`[关闭状态] → [打开状态]`
   - 对：分别画出两个按钮卡片，各自包含图标、名称、状态描述

4. **弹窗要还原完整结构**：标题 + 正文 + 按钮操作区

5. **编号标注区用 Markdown 标题层级**：`#### ③ 门开关` → 段落文字 → ASCII（如有流程图）

6. **表格数据用 Markdown 表格**：变更记录、颜色对照、开关选项等结构化数据

7. **Toast/提示文案用行内代码**：`` `"请在车辆上电状态进行操作"` ``

## OCR-视觉修正对照表

文档末尾必须包含修正表，格式：

```markdown
## OCR 与视觉识别对照备注

> 以下标记 OCR 原文中存在识别偏差、由视觉识别修正的内容：

- Page N: OCR 原文 `[错误文本]` → 视觉修正为 `[正确文本]`
```

常见 OCR 错误类型：
- 形近字混淆：`关阅`→`关闭`、`儿幸锁`→`儿童锁`、`急躁`→`踩下`
- 漏字/多字：`ES功能关`→`ESC功能关闭`
- 标点错误：`"已留窗通风"` 的引号识别为 `"`
- 深色背景小字号：识别率显著低于白底大字

## 质量检查清单

- [ ] 采用混合策略：段落文字用 Markdown 格式化，UI 元素用 ASCII 还原
- [ ] **ASCII 还原忠实原PDF空间布局**，没有按功能/主题重新组织内容
- [ ] 表格数据用 Markdown 表格，非 ASCII 框线
- [ ] Toast/提示文案用行内代码 `` ` `` 包裹
- [ ] 编号标注区用 Markdown 标题层级 `#### ③ xxx`
- [ ] 编号标注区域完整覆盖，无遗漏
- [ ] 按钮/弹窗/开关的 ASCII 还原准确反映了视觉布局
- [ ] OCR 错误已通过视觉交叉验证修正
- [ ] 修正表列出了所有发现的 OCR 偏差
- [ ] 没有凭空猜测的内容（不确定处明确标注）
